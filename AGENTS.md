# digital-dome — Notes for AI Agents

A small web application firewall: [dome](dome) holds the engine (`dome.New(clientIP, options...)`, `VerifyRequest`, `HandleError`, `Block`), [dome4echo](dome4echo) adapts it to Echo middleware. The [root README](README.md) covers features and configuration; the [dome4echo README](dome4echo/README.md) covers the adapter's contract. Both are current.

- **One `Dome` instance holds ALL per-IP block state — the whole process must share a single instance.** Two instances are two independent WAFs that never see each other's counts. If your wiring builds services before the Dome exists (a DI factory), inject a lazy accessor (`func() *dome.Dome`) instead of calling the factory eagerly at construction time; eager resolution through a not-yet-wired parent is a nil-deref waiting for the first test that builds a bare factory.

- **The per-IP tracker only fires if errors actually reach `HandleError` — three silent no-op configurations.** (1) A handler that renders its own error response and returns `nil` to the router never feeds the Dome; for application policy that never surfaces as an error (a failed sign-in that renders a 403 page itself), call `Dome.Block(request)` directly — that is exactly what it exists for. (2) `HandleError` classifies errors with `derp.ErrorCode`, so a non-derp error reads as 500: it matches neither the default `blockStatusCodes` (403) nor `logStatusCodes` (404), and `derp.IsClientError` is false so soft-blocked paths don't count it either. Errors must carry derp status codes to move the needle. **`dome4echo` translates `*echo.HTTPError` for exactly this reason** — Echo answers its own routing failures (404, 405) with that type, and left alone every one of them would be filed as a server error, which makes `LogStatusCodes(405)` silently impossible and hides a scanner behind a status the application never sent. Any new router adapter owes its framework the same translation. (3) Request logging is entirely off until `LogDatabase(collection)` is set — that is the intended default, not a bug.

- **`HandleError` may REWRITE the error, and its return value is the one to propagate.** A client (4xx) error on a soft-blocked path comes back as a `derp.Forbidden` wrapping the original. Middleware must `return d.HandleError(request, err)`, never the original `err` — [dome4echo.go](dome4echo/dome4echo.go) does this correctly; copy that shape in any new adapter.

- **`dome.RemoteAddr` trusts only the TCP peer (`net.SplitHostPort(request.RemoteAddr)`), never request headers — unspoofable, but wrong behind a proxy.** Behind Cloudflare or a load balancer every score lands on the proxy's IP, so inject a proxy-aware `ClientIPResolver` (realclientip-style) instead. The one header Dome does read, `X-Forwarded-Host` in `trueHostname`, feeds only the URL field of a log record and never a blocking decision — trusting it there is deliberate, don't "harden" it.

- **`With()` is setup-only.** It swaps matchers and the cache with no synchronization; calling it once requests are in flight races with `VerifyRequest`/`HandleError`. Configure at startup, then leave the Dome alone.

- **All list matching is substring (Aho-Corasick), not exact or prefix — with one deliberate exception.** `.php` blocks every path containing it anywhere; `Claude` blocks any User-Agent containing it. A short new entry in `BlockUserAgents`/`BlockPaths` can over-block wildly — check what it's a substring of before adding. The exception is `BlockQueryParams`, which matches a query parameter **name** exactly, and must stay that way: a query *value* is attacker-controlled, so a substring rule over the whole `RequestURI` would fire on any link preview or oEmbed lookup whose target URL merely mentions the pattern. That is also why matching `BlockedPaths` against `RequestURI` is the wrong way to catch a query-string probe.

- **A blocked path catches only half of a probe when the framework offers a query-string spelling.** WordPress serves its whole REST API from `?rest_route=` under plain permalinks, so `/wp-json` in `BlockedPaths` misses `/?rest_route=/batch/v1` entirely — same endpoint, a path of `/`, no match. When adding a framework signature, check whether that framework has a second entry point, and put it in `BlockedQueryParams`.

- **`BlockedPaths` is hard and `SuspiciousPaths` is soft, and the choice turns on whether the HOST application might serve the same shape.** Archive extensions (`.zip`, `.sql`, …) and `/@fs/` are soft for exactly that reason: a real export answers 200 and never counts, while a scanner's guess 404s and does. Hard-blocking them would break a feature in an application that builds archives or whose own URL namespace starts with `@`.

- **Block mechanics: blocking begins on the 6th error (`count > 5`), and every increment refreshes an escalating TTL** (1 minute under 10 errors, `2*count` minutes up to 60, capped at 2 hours — [utilities.go](dome/utilities.go) `getTTL`). In dome4echo a blocked request's own 403 is fed back through `HandleError`, and 403 is in the default `blockStatusCodes`, so hammering while blocked renews and escalates the block — intentional, not double-counting.

- **The blocked-IP cache is in-memory and per-process (otter).** Multi-node deployments divide an IP's count across nodes and restarts wipe it. This layer catches one IP misbehaving against one process; cross-node defense (e.g. a per-username window in shared storage) belongs in the application, not here.

- **An empty `User-Agent` is always rejected and `New(nil)` panics — both by design.** There is no option to allow UA-less requests, and the `ClientIPResolver` is a required first argument because a Dome without a client-IP strategy is meaningless.

- **`incrementBlockCount` takes a sharded mutex because otter has no atomic update.** The read-modify-write under the shard lock is what keeps concurrent errors from one IP from losing increments — do not "simplify" it to a bare `Get`+`Set`.
